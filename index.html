FHE · TFHE-rs · programmable bootstrapping

Encrypt two numbers in your browser, let an untrusted Oracle add the ciphertexts it can never read, then decrypt the sum locally.

WHY IT MATTERS

Fully homomorphic encryption lets a server crunch data it is never allowed to see. That unlocks private cloud analytics on medical, financial, and genomic records — outsourcing computation without ever surrendering the plaintext or the key.

THE QUESTIONER

Your keys. Your values. Your world.

HOW THIS DEMO WORKS

  1. Your browser generates keys and encrypts your numbers.
  2. Only ciphertext is sent over the wire to the Oracle.
  3. The Oracle adds ciphertexts and returns ciphertext.
  4. Your browser decrypts locally and reveals the sum.

This is Fully Homomorphic Encryption (TFHE-rs, programmable bootstrapping bootstrapping = noise reset). The “plaintext world vs ciphertext world” panel below shows why the encrypted result decrypts to the right answer.

The Oracle is a demonstration server: it is for demonstration only and should never receive real sensitive values.

WHEN THE SERVER IS MALICIOUS

An evaluation key cannot directly decrypt. But FHE does not authenticate the server's answer: a malicious server can return altered ciphertext. In a different TFHE/FHEW application, researchers recovered a client key by inducing decryption errors and repeatedly learning from the client's reports of those errors. Here the decrypted result and match/mismatch verdict stay in your browser; this page sends neither back to the Oracle. That closes this particular feedback path, not every possible client side channel. Original attack (2022) · FHE side-channel survey (2025)

PROGRAMMABLE BOOTSTRAPPING & THE NOISE BUDGET

Every TFHE ciphertext hides its value under random noise. Each operation grows that noise; too much and decryption fails. Programmable bootstrapping (PBS) resets the noise on every operation so you can keep computing — but each reset is expensive, which is why real FHE programs stay small.

The swatch and digest are a fingerprint of the actual ciphertext bytes. Encryption is probabilistic: re-encrypt the same number and this fingerprint changes — yet the Oracle still adds the two ciphertexts to the correct sum.

FheUint8 multiply is offered by TFHE-rs too, but each multiply triggers many more programmable bootstraps than an add, so it is far slower and heavier — the Oracle ships add only to keep the round-trip snappy. Homomorphism is general; the cost is what varies per operation. You do not have to take that on trust: the local multiply bench below performs real homomorphic multiplications in this tab, on a scheme with no bootstrapping, so you can watch the noise budget run out and see exactly what TFHE is paying for.

PLAINTEXT WORLD vs CIPHERTEXT WORLD

Homomorphism means the same computation runs in both worlds and the answers match: Enc(a) ⊞ Enc(b) decrypts to a + b. Both worlds use the same 8-bit type, so both wrap at 256 — the plaintext track adds as a u8 and FheUint8 does the same. Encrypt and compute above, then watch both tracks fill in.

Nothing here is being asserted on your behalf.

WHY ADDING NOISE STILL ADDS: PEEK INSIDE ONE CIPHERTEXT

A TFHE ciphertext is not a locked box holding your number — it is your number plus a pile of random noise. The Oracle can add two of these piles without ever separating value from noise, which is exactly why it computes but cannot read. Open the peek to see one small value buried under that noise.

Enc(3) = 3 + 71942850 random noise (hides the 3)
Enc(4) = 4 + 36180927 different random noise
the Oracle adds them slot-by-slot ↓
Enc(7) = 7 + A7BC2177F3D9 noise grew (both piles added)
  • Value + noise, added together: adding the two ciphertexts adds both the hidden 3 and 4 (giving 7) and both noise piles — so the result is a noisier encoding of the correct sum. Your secret key subtracts the noise away; the Oracle has no key, so to it the whole strip is random.
  • Why bootstrapping exists: each add grows the noise strip. Do too many and the noise overruns the value slot — decryption returns garbage. Gate bootstrapping resets the noise back down after each gate, at real cost, so the computation can keep going. That is the rise-then-reset the noise budget above is about.

LOCAL MULTIPLY BENCH — SPEND THE NOISE BUDGET YOURSELF

The Oracle above does the addition, because Zama's browser build of TFHE-rs ships key generation, encryption and decryption only — it exposes no evaluation operations at all, so the homomorphic step has to run where that API exists. This bench needs no oracle and no network. It runs a second, much smaller homomorphic scheme entirely in this tab, and it will do the multiplication the button above only describes.

Toy scale, stated plainly. This is DGHV (van Dijk–Gentry–Halevi–Vaikuntanathan, 2010) in its symmetric form: Enc(m) = m + 256r + qp, Dec(c) = (c mod p) mod 256, with a 48-bit secret p. The original scheme needs a modulus of millions of bits before its hardness assumption means anything, so this is not secure encryption and must never be used as such. What is exactly right about it is the arithmetic: addition adds the noise, multiplication multiplies it, and when the noise passes p/2 decryption stops being correct. That ceiling is the reason TFHE bootstraps.

What is Fully Homomorphic Encryption?

      

        
FHE lets a server compute on your encrypted data without ever decrypting it.

        

          TFHE-rs uses programmable bootstrapping (PBS): every operation refreshes
          the ciphertext noise, so you can keep computing without hitting a fixed circuit-depth wall
          — unlike leveled schemes that budget for a preset number of operations.
        

        

          But bootstrapping is not free. Each block-level operation pays a real bootstrapping cost,
          so in practice FHE programs stay small and slow — the response time shown for even a
          single add is the price you are watching. FHE removes the depth limit; it does not remove
          the cost.
        

        

          The subtle part: the server holds only an evaluation key. It can transform
          ciphertexts (including bootstrapping) but cannot decrypt with that key. The client secret
          key never leaves your browser. A malicious server may still learn from a client that
          reports decryption failures; this demo keeps that verdict local.
        

        
This is the real thing — with real limits, honestly shown.
